# Neoism Servo runtime

The **actual** Servo browser engine for interactive artifacts, packaged as the standalone `neoism-servo-runtime` executable. This directory has its own `[workspace]` and must remain excluded from the root Neoism workspace and dependency graph. Servo's FreeType 0.23 native link cannot coexist in Cargo's graph with Sugarloaf/font-kit's FreeType 0.20, even if Servo were optional. The IPC frontend at `../interactive-artifacts` has no Servo dependency.

Servo v0.5.0 is pinned to commit `1d44e5dd6a8b64c02f9dbf7fcbdf4ebdd0740019`; it declares MSRV 1.88 and uses development toolchain 1.95. This worker and its independent lockfile are checked on Neoism's working Rust 1.92 toolchain. Cargo's incompatible-Rust-version fallback avoids newer-MSRV transitive selections when resolving on 1.92. Worker toolchains may be selected explicitly without changing the root application's toolchain/configuration.

```sh
CARGO_BUILD_JOBS=2 cargo build --locked --manifest-path neoism-frontend/servo-runtime/Cargo.toml
python3 neoism-frontend/servo-runtime/tests/live_worker.py
# Debug executable: neoism-frontend/servo-runtime/target/debug/neoism-servo-runtime
# Desktop dev discovery/sibling deployment is owned by the frontend host.
```

Default Servo features are disabled; baked-in resources and bundled FreeType are enabled. No default system clipboard, JS JIT, WebGPU, XR, gamepad or GStreamer. The worker installs a Rustls crypto provider inside **its own process only**; it never changes the Neoism application's provider. CPU frame transport uses Servo's real `SoftwareRenderingContext`, painting and safe `read_to_image` API. Native surfman/software GL and font/library prerequisites remain required. CPU transport is not a fake portable renderer, and a functioning software adapter (Mesa/EGL/OSMesa or platform equivalent) is required.

`src/engine.rs` owns ServoBuilder, WebViews, delegates, synthetic resource interception, viewport/theme changes and genuine Servo input. New source revisions replace the WebView; styles/theme/viewport/visibility changes preserve the live DOM/JS state. Internal request generations reject all old-epoch pipe replies, including destroy/recreate. Frame sequences increase across view replacements. In-process engine initialization happens once in each helper. `src/main.rs` owns the bounded control reader, engine-thread pumping, frame serialization and lifecycle. Servo stays on the worker's main thread. It pumps on engine wakes and bounded animation ticks and sleeps waiting for events when static/hidden. Offscreen iframes remain shown to preserve their compositor scenes; `set_throttled(!visible)` gates Servo's internal refresh driver and JS timer rate, at creation, committed load completion (the initial call can precede the pipeline), and visibility transitions. CPU painting, readback and publication for continuous animation are capped at 30 FPS per view. Dirty state is retained until presentation, and the main worker's idle receive includes the earliest pending deadline even when animation stops, so a final/static frame cannot be stranded. Once the final frame is presented, static input/load updates incur no animation cadence delay. First readback and live style application wait for the completed synthetic-origin document. Parent pipe threads never transport GL/GPU handles. Before Servo initialization, a safe filedescriptor API preserves the original stdout pipe for protocol writes and redirects process stdout to stderr. Rust/native engine diagnostics cannot contaminate the binary protocol; only the saved descriptor carries IPC.

The executable requires `--stdio --experimental`. Standard input/output are protocol version 1: bounded JSON requests/metadata and binary owned RGBA frames, as defined in the frontend `ipc` module. Standard error is inherited for diagnostics. The parent launches a specific executable, not a shell. No listener/socket or local-file navigation is created. Worker startup is asynchronous to the GUI; failures are delivered through the frontend diagnostic mailbox. Upstream shutdown may hang; frontend shutdown grants 500ms then kills/reaps the worker off the GUI thread.

## Policy, not sandbox

There is **no OS sandbox**. The worker runs with the same user privileges as Neoism. Process separation does not contain filesystem/network access by an engine exploit, supply memory/CPU quotas or establish audited security guarantees. Experimental trusted-content opt-in remains required. Each view receives a unique synthetic HTTPS `.invalid` URL; only its exact initial document GET is intercepted with document bytes. Every other intercepted resource is cancelled, including engine-level unassociated requests. The pinned `components/net/fetch/methods.rs` calls interception before native protocol selection, so this policy also covers file/data/blob loads despite the delegate documentation mentioning HTTP/HTTPS only. Navigations are explicitly denied except the initial synthetic one; popups, permissions, clipboard and native controls are denied/cancelled. Restrictive response-header CSP permits inline JS/CSS but denies external resources, connections, frames, workers, forms and objects. Service/shared workers, privileged helpers/testing APIs and directory listings are disabled. This interception/CSP coverage is not security-audited.

No privileged host bridge, custom privileged protocol, arbitrary host-exposed JS evaluation API or height channel is supplied. The only evaluation is an internal host-controlled style script: validated standard CSS variables from the selected `ArtifactStyles` snapshot, root inline color-scheme and a fixed `neoism-theme-changed` window notification. The initial HTML bootstrap JSON escapes `<` and Unicode line separators and runs before author scripts. Fonts are serialized CSS-escaped family values, never raw script/CSS concatenation. Default body background/foreground/sans font and monospace rules use those variables. Later updates do not reload: before serving they replace initial bootstrap bytes; afterward they wait for the committed synthetic-origin document to complete, check origin/root in JS, and retry false results. Superseded style callbacks are ignored; CPU readback is blocked until the current style evaluation completes. Canvas/SVG charts can re-read semantic/chart CSS variables on the event. Pointer/wheel/key/IME are actual engine input events, not JavaScript injection; native IME candidate and selection UI feedback is a remaining integration gap.

## Verification status

**PASS:** `CARGO_BUILD_JOBS=2 CARGO_RESOLVER_INCOMPATIBLE_RUST_VERSIONS=fallback cargo +1.92 check --manifest-path Cargo.toml --all-targets` against the actual pinned git Servo dependency. The independent Cargo.lock is included. A prerelease API drift needed `pkcs1 = "=0.8.0-rc.4"`, matching Servo v0.5.0's release lockfile; newer rc.5 is incompatible with its RSA rc.18. No upstream source patch or root dependency workaround is used.

**Live debug verification PASS:** built the actual executable with Rust 1.92 using `CARGO_BUILD_JOBS=2 cargo build --locked --manifest-path neoism-frontend/servo-runtime/Cargo.toml`, then ran `tests/live_worker.py` against its binary stdio protocol on the available Linux display, offscreen only. Real RGBA page pixels passed at 320×280 (358,400 bytes) and 400×300 (480,000 bytes). Actual pointer clicks changed a counter, a physical keyboard event typed `x` into an input, rAF changed pixel colors without parent Pump commands, live theme changed the background from `(18,52,86,255)` to `(101,67,33,255)` while retaining counter/input state, resizing retained that state, stopping rAF allowed the static worker to sleep and a third click woke it, blocked fetch rejected, a local HTTP server received zero requests, and Shutdown exited successfully. Binary stdout contained only valid protocol packets. The same complete harness also passed with `LIBGL_ALWAYS_SOFTWARE=1 GALLIUM_DRIVER=llvmpipe`, in addition to the display's default Mesa adapter. This is native execution evidence, not just cargo-check or a mock renderer. No release build, additional GUI window, toolchain/profile changes or frontend source modifications were used.

The live harness also encodes author-JS rAF and `setInterval` counters into source pixels on real pointer input, tests both initially hidden documents and hidden transitions, applies styles while hidden, and measures process CPU time via Linux `/proc/<pid>/stat` when available. Frame arrival timestamps check the visible 30 FPS cap. It checks every initial/resume background publication, all raster bytes across 12 hide/show cycles, legitimate white content, animation's final retained frame, and ten static one-shot inputs without parent Pump requests. `NEOISM_PERF_BASELINE=1` reports performance and first/resume-publication assertions instead of failing them, allowing the same fixture to quantify a saved pre-fix binary; eventual source-pixel, input/state and scroll-cycle assertions remain mandatory. No privileged JS bridge, arbitrary evaluation API, or engine test-helper preferences are introduced.

The live fixture deliberately hides its denied-image test element: Servo's visible broken-image placeholder otherwise covers the background probe in white, which is not a theme/context failure. Unsuccessful diagnostic context/renderer experiments were removed; the verified binary uses the original pinned Servo engine and SoftwareRenderingContext, without vendored upstream patches or new rendering dependencies. The reusable harness uses bounded phase/read/shutdown deadlines and kills/reaps only its own child on failure. Runtime logs are under this directory's `target/live-worker.result.log` and `target/live-worker.stderr.log`. Cross-platform packaging remains separate; native linked engine unit tests are not claimed executed.

### Worker performance regression verification

A saved pre-fix debug worker and the rebuilt worker were exercised with the same source fixture. Representative native Linux samples (process CPU seconds aggregate all worker threads; hidden/resume counter deltas include the short visible snapshot transitions):

| Measurement | Pre-fix llvmpipe | Fixed llvmpipe | Fixed default Mesa |
| --- | ---: | ---: | ---: |
| Visible publications over 1.5 s | 184 / 122.66 FPS | 40 / 26.67 FPS | 40 / 26.67 FPS |
| Visible process CPU over 1.5 s | 3.09 s | 1.79 s | 1.75 s |
| Hidden process CPU over 1.2 s | 0.23 s | 0.02 s | 0.02 s |
| Hidden/resume rAF counter delta | 46 | 6 | 7 |
| Hidden/resume 10 ms timer counter delta | 131 | 4 | 6 |
| Initially hidden rAF / timer snapshot | 62 / 175 | 4 / 2 | 4 / 3 |
| Ten static input latencies | 16.2–25.7 ms | 18.0–24.1 ms | 16.4–26.5 ms |

Both fixed-worker runs exited successfully with all source-pixel/state checks, every first/resume publication, 12 full-raster hide/show cycles, legitimate white theme, hidden style updates, bounded hidden JS progress, visible author-JS progress, 30 FPS publication cap, final animation frame, and static one-shot inputs passing. The old worker also exposed a white initial publication, now rejected by the first-frame load guard. The pacing wait is at most one 33.333334 ms interval; static work after animation settles has no artificial cadence wait. Synchronous rendering/IPC and OS scheduling are additional costs, so these measured end-to-end latencies are evidence, not a cross-machine real-time guarantee.

Final debug build used `CARGO_BUILD_JOBS=2 cargo build --locked --manifest-path neoism-frontend/servo-runtime/Cargo.toml` and finished in 19.97 s. Native worker unit tests passed (5 library tests and 2 receive-deadline tests; test build 31.20 s). The isolated verification workspace additionally passed 24 facade/IPC contracts and 3 style-script tests. No root app build, release build, profile change, frontend/desktop modification, dependency change, privileged bridge, or upstream Servo source modification was used. The existing root debug worker symlink still resolves to the newly compiled standalone debug executable. Evidence is saved under `target/perf-build.log`, `target/perf-unit.log`, `target/perf-contract.log`, `target/perf-before.log`, `target/perf-after-llvmpipe.log`, `target/perf-after-mesa.log`, and the two corresponding saved stderr logs.
