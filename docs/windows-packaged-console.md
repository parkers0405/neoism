# Windows packaged launcher and console ownership

The production installation starts `neoism.exe`, a Bun-compiled `gpuix/src/cli.ts` launcher. It imports `launch.ts`, then the hashed `web/app/main-*.js` module and its bytecode. These are native GPUIX resources, not an Electron/browser launcher. Changing a Rust desktop binary's `windows_subsystem` does not affect this executable. `gpuix/scripts/build.ts` requests `compile.windows.hideConsole: true` and now inspects the actual emitted PE subsystem before publishing it. Subsystem 2 is GUI; subsystem 3 is console. A GUI subsystem prevents the initial Explorer launch from allocating a console, but does not suppress independently launched console children.

Current local startup uses Bun's `node:child_process.spawn` with `windowsHide: true`, non-detached Windows spawning, and log-file stdio. Persistent hosting in `gpuix/native/src/service_process.rs` uses `CREATE_NO_WINDOW`; Fast hosting in `neoism-agent-service-api/src/fast_hosting.rs` also uses it. Those flags must remain on the actual console child creation, not be replaced by hiding an already-created window. The separate CLI update helper previously omitted `windowsHide`; it now requests it explicitly while preserving stdio and exit status. PTY/ConPTY launches are deliberately unchanged.

Microsoft documents that `CREATE_NO_WINDOW` is ignored with `DETACHED_PROCESS` or `CREATE_NEW_CONSOLE`, and ignored for non-console executables. `DETACHED_PROCESS` itself prevents inheriting the parent console; combining it with `CREATE_NO_WINDOW` is redundant, not proof of a console flash. A process group is not a console-hiding mechanism. Bun 1.3.13's `js_bun_spawn_bindings.zig` explicitly reads `windowsHide` and forwards it as `SpawnOptions.windows.hide_window`; it is a supported option, not an arbitrary ignored Node-only property. Do not infer that all Bun spawns need replacing with native wrappers.

The supported full release invocation, `node scripts/build-gpuix-release.mjs`, builds the Rust services from the checkout, then overrides `NEOISM_GPUIX_WORKSPACE_DAEMON` with `target/release/neoism-workspace-daemon.exe` before compiling the frontend. In contrast, ad-hoc `build.ts` packaging permits an explicit override and otherwise prefers `gpuix/artifacts` over `target/activation`; either can be stale. Runtime selection also prefers an explicit override, then the daemon beside `process.execPath`. An updated JS module alone cannot update daemon authentication behavior in an old sibling executable.

Both Windows archive packaging and direct MSI packaging now reject a console-subsystem launcher or service bytes different from `target/release`. Archive validation repeats after extraction, and build metadata records service SHA-256 hashes. This establishes identity with the full release build's outputs, not cryptographic proof that an arbitrary local `target/release` was built from HEAD. The release orchestration's Cargo build is still required; the gate cannot establish what an existing installation contains without obtaining those artifacts or their hashes.

The reported Host Server `neoism-fast-daemon-*` association-401 error concerns authentication with the shared Agent, not evidence that this process allocated a console. Current Fast-host spawn already suppresses console creation. Identify the installed launcher's PE subsystem and the visible console's owning process/command line on real Windows before attributing that symptom to another subprocess. No Windows runtime observation was available for this change.
