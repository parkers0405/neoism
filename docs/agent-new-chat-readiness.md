# New-chat readiness: lifecycle and warm-state preservation

## What opening a chat actually does

Desktop `NeoismAgentPane::create_new_session` (`neoism-frontend/desktop/src/neoism/agent/commands.rs`) resets conversation/transcript/composer runtime state, not model/provider readiness. `ensure_session` posts the new session and does not invalidate the provider catalog. Opening a separate tab (`screen/bridges/agent.rs::open_neoism_agent_tab`) constructs another pane; its `apply_config_defaults` calls `refresh_provider_readiness`, which first uses pane readiness and then the process catalog cache. A new chat does not inherently require account rediscovery.

The desktop process catalog key is `(CatalogScope, resource)`. Scope includes normalized daemon endpoint, daemon credential, exact directory and an endpoint revision. Re-registering the same daemon credential is a no-op. Changed credentials and successful provider-account mutations invalidate the endpoint revision/cache. Different directories remain separate because they can resolve different provider configurations. Complete positive pane/process readiness has a five-minute admission lifetime; process HTTP freshness is thirty seconds. Refresh is background-only. New tabs can reuse a complete process snapshot without a new provider worker, even after the HTTP freshness interval.

The server's `AppState::try_plugin_snapshot_for_tenant` reuses the tenant/workspace runtime's plugin generation. `plugins::build_host_with_config` constructs a `ProviderPlatform`/`ProviderRegistry` for that generation, not for every new chat. Account metadata belongs to its shared `OpenAiClient`. A new generation, workspace, daemon process, credential identity or discovery source can legitimately start cold.

## Actual avoidable loss

`provider_openai.rs::codex_models_with_credentials` formerly passed an owned cache mutex guard into the background OAuth/discovery task. It held that guard throughout credential refresh and HTTP/body reads. During a refresh, another reader could not even inspect an already loaded catalog and returned pending. A refresh failure then replaced the good snapshot with `None`. That was a loss of previously discovered metadata, not evidence that the account had no models. The prior pending/fallback guard alone did not solve this.

The snapshot now uses a short-lived `RwLock`, and a separate mutex owns single-flight refresh. Same-identity readers keep using the real discovered catalog while refresh is in flight. Failed refresh preserves its original `fetched_at`, backs off fifteen seconds, and permits bounded stale reuse for at most thirty minutes from the last successful discovery. Failure never renews that age. Successful discovery replaces the snapshot, including a successful empty result.

Desktop pane and process-cache application could also replace a complete snapshot with a later pending/basic-catalog response. They now retain the complete snapshot only within its original five-minute lifetime and only when both responses carry the same nonempty `readinessIdentity` and connected-provider list. Retention does not renew its timestamp. A complete empty response, disconnect, expired snapshot or different identity still supersedes it. The shared pane uses the same bounded identity rule, does not clear readiness merely to refresh defaults or open the connection picker, and clears it on actual endpoint/directory changes and credential mutations.

`readinessIdentity` is an opaque SHA-256 fingerprint captured from the exact OAuth snapshot supplied to discovery. It covers access token, account ID, discovery endpoint and client version. It is not inferred from a model/account display label. Raw tokens are not exposed. Token rotation deliberately changes identity; the post-refresh cache recheck and publication use the persisted rotated identity. A result under one token/account/source is not lent to a different identity. An independently rotated credential can require fresh discovery; clicking New Chat alone cannot cause that rotation or invalidate the loaded snapshot.

The account-reconciliation follow-up also exposed two failing shared connection tests: the code computed a remembered/explicit connection ID but used it only to preselect an account picker. It reopened that picker even when the remembered account was still present, and silently replaced a deleted explicit account with the sole remaining account. `apply_provider_connections` now validates and reuses a still-present selection when reconciling the unchanged/restored model, and reports a missing explicit selection instead of substituting credentials. Explicitly switching to another model retains the existing multi-account confirmation picker and selected-row highlighting. This is separate from model discovery and does not authorize an account from its label.

## Why visible chips are not proof of discovery

`api.rs::fetch_config_defaults` reads `/v2/config/defaults`; `render_state.rs::apply_loaded_config_defaults` applies configured model/thinking preferences without requiring account model discovery. `pane/input.rs::current_model_picker_option` even constructs a selected row from `self.model` when no loaded option matches it. Saved session hydration can supply the same strings. Consequently a visible model/thinking chip can be configuration or a saved selection, rather than a previously discovered account capability. The original report alone does not establish which source populated those chips.

The lifecycle regressions intentionally use an `account-only-model` absent from the fallback response. They establish that real previously loaded metadata survives new-chat creation, a separately constructed same-scope pane, an in-flight refresh, and refresh failure. Other tests establish that pending basic discovery still validates selections, invalid drafts are retained, successful empty discovery is authoritative, stale metadata expires, and different credentials/accounts/endpoints/scopes cannot borrow the preserved snapshot.
