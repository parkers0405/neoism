**2026-07-16:** deleted `vendor/fff-search` (+ its `[patch.crates-io]` override in root Cargo.toml + its NOTICE entry) and switched to the published crate: `fff-search = { version = "0.10.1-nightly.31be224", default-features = false, features = ["ripgrep"] }` (newest at the time; stable was 0.10.0, both released 2026-07-16; original vendored copy was `0.9.4-nightly.8092cfa`). User wants the newest upstream fff, not a local fork. Sub-crates (fff-grep, fff-query-parser) resolve transitively from crates.io.

**CRITICAL gotcha — the `ripgrep` feature is mandatory:** fff-search's default features are `["ripgrep"]` (pure-Rust globset glob backend). With `default-features = false` and NEITHER `ripgrep` NOR `zlob` enabled, fff-search 0.10.x **fails to compile ITSELF** — `src/index/constraints.rs` calls `compiled_matches`/`match_glob_pattern`/`compile_one`, which are `#[cfg(feature="zlob")]` / `#[cfg(all(not(feature="zlob"),feature="ripgrep"))]`. So one glob backend must be on. Chose `ripgrep` over `zlob` because `zlob` is a native/FFI SIMD backend (complicates mac/win/OSS builds); ripgrep is pure Rust. Verified: `cargo check` clean for neoism-agent-server, neoism (desktop), neoism-workspace-index.

**Where fff is used:** library API, not a CLI. Agent tools live in `neoism-agent/crates/neoism-agent-server/src/tool_support/fff.rs` — a clean wrapper exposing `fffind` (FilePicker::fuzzy_search), `ffgrep` (grep), `fff_multi_grep` (multi_grep), with a per-root `PICKER_CACHE`. Desktop uses fff-search for the Alt+S finder. API used (FilePicker::new_with_shared_state, fuzzy_search, grep, multi_grep, QueryParser, AiGrepConfig, GrepMode, FilePickerOptions, SharedFilePicker/SharedFrecency, PaginationArgs, has_regex_metacharacters) is unchanged in 0.10.x — the wrapper compiles as-is. This wrapper is the INTENDED integration ("how fff is used"); deleting it would remove the agent search tools.

**MCP question answered:** fff ships an MCP server crate `fff-mcp`, BUT that is for EXTERNAL agents (Claude Desktop, Cursor) bolting fff on over MCP. The newest opencode (`~/projects/neoism/opencode`, the fff-using copy — others don't reference fff) uses `@ff-labs/fff-bun`, fff's IN-PROCESS Bun FFI binding (`packages/core/src/filesystem/fff.bun.ts` + `search.ts`), NOT the MCP server. That is the analog of our in-process Rust library linking. So embedding agents (opencode AND neoism-agent) use fff in-process; nobody uses fff-mcp for their own tools. Our library approach is correct — do NOT switch the agent to MCP (would add process + JSON-RPC overhead).

**Mac slowness ROOT CAUSE + FIX (aligned to opencode, 2026-07-16, cargo-check clean):** the lib default is `enable_content_indexing:false` and opencode leaves it default; our agent wrapper FORCED it `true` → built a RESIDENT content index of the whole tree (reading every file) on first query behind `wait_for_scan` (15s) = the mac first-hit freeze. mmap default is false in BOTH lib and opencode (so mmap was a red herring, left as-is). And `GrepSearchOptions.time_budget_ms` defaults 0=unlimited; opencode passes `timeBudgetMs:1500` (partial results). Changes made to `tool_support/fff.rs`: (1) `enable_content_indexing: false`; (2) grep `time_budget_ms = timeout_ms.saturating_sub(2000).max(500)` on ffgrep (both primary+fuzzy) and fff_multi_grep → partial results before the outer hard-kill instead of a timeout error; (3) wired `abort_signal = context.cancel.clone()` so fff self-cancels mid-search. Desktop finder (`host/finder_search.rs`) was ALREADY opencode-style (Default content-indexing off, `time_budget_ms:35`, `max_matches_per_file:25`). Daemon search (`workspace-daemon/src/search.rs`) uses `rg` subprocesses by design, not fff. **Deliberate deviation from opencode:** did NOT copy `enableFsRootScanning/enableHomeDirScanning: true` — those index the whole filesystem/home (opencode wants cross-project @-mentions), which would make mac SLOWER, opposite of the goal; kept both false (project-scoped). `bash` tool mac slowness still NOT investigated.

**Edge fixes (2026-07-16, cargo-check clean):** (1) **ffgrep "worker panicked"** — a data-dependent panic INSIDE fff-search (couldn't repro with ~35 query variants: regex/plain/fuzzy pipes, include-globs, high-volume, context, multi_grep — so it's file-content specific). Root harm: the panic dropped fff's RwLock read guard DURING unwind → POISONED the cached SharedFilePicker → every later query on that root failed too (why it "reproduced exactly"). Fix in `tool_support/fff.rs` `with_picker`: wrap `operation(picker)` in `catch_unwind` (catches BEFORE guard drops → no poison), on panic evict the root from PICKER_CACHE (next call rebuilds fresh) and return a real error via `panic_payload_message()` instead of a bare "worker panicked" — so next occurrence surfaces fff's ACTUAL panic message to pinpoint/report upstream. (2) **fffind oversized/conceptual query → 0 files** — long natural-language query fuzzy-matches no PATH; added fallback in `fffind_tool_sync`: on empty results retry `fuzzy_search` on the single longest (≥3-char) token so relevant files still surface.

**Overflow root-cause + fix (2026-07-16, the panic-message extraction paid off):** the caught panic was `attempt to multiply with overflow` — an integer-multiply overflow in fff's REGEX path building/scoring a wide alternation (~35 branches; debug build → overflow panics). NOT result-count (lowering limit 250→25 didn't help). Fix in `ffgrep_tool_sync` (tool_support/fff.rs): `literal_alternation_terms()` detects a pure literal OR (`a|b|c`, every branch free of regex metachars) and routes it through `picker.multi_grep()` (Aho-Corasick) instead of one wide regex — the correct + faster engine for literal OR, and it sidesteps the overflow. Non-literal alternations stay on regex and are covered by the catch_unwind safety net. `used_mode` reports "multi" for that route.

**CORRECTION + real fix (2026-07-16, runtime-confirmed):** the overflow is NOT the regex path — the actual panic (from the user's `./target/debug/neoism` stderr) is `grep/fuzzy_grep.rs:66:21 attempt to multiply with overflow` on fff's INTERNAL worker threads (`fff-search-N`). `fuzzy_grep_search` computes `perfect_score = (grep_text.len() as u16) * 16` where grep_text is the NEEDLE → u16 overflow once needle ≥ 4096 bytes. CRUCIAL: it's a WORKER-thread panic, so the `with_picker` catch_unwind does NOT catch it — the tool HANGS (user had to Ctrl+C), so it must be PREVENTED, not caught. Fix in `ffgrep_tool_sync`: `MAX_FUZZY_NEEDLE = 1024` — skip the fuzzy fallback and downgrade an explicit `Fuzzy` mode to `PlainText` when `pattern.len() > 1024`. Combined with the literal-alternation → multi_grep route, all paths to fuzzy-with-a-huge-needle are closed. Runtime-verified: PlainText grep w/ 6000-char needle = Ok(0), multi_grep w/ 2000 terms = Ok(80), neither overflows. (fff upstream bug: should use u32/saturating at fuzzy_grep.rs:66.)
