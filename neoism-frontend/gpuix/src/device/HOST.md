# Native device host adapter

`host.ts` is renderer-independent and imports no process helpers at module evaluation. Only `startSession()` dynamically loads `ffmpeg.ts`; the feature-off application must not import a device UI entry point. The caller supplies an existing `http(s)` expo-device-hub URL (including an optional reverse-proxy prefix and query credentials). Nothing discovers, installs, downloads, or starts a hub, emulator, or simulator automatically. Use a trusted hub/network: device streams and input carry sensitive information. Use HTTPS for remote connections.

## Integration API

```ts
const host = new DeviceHost({ url: userProvidedHubUrl, ffmpegPath: optionalExecutablePath });
const { devices, warnings } = await host.listDevices();
// Only inside an explicit Boot click handler:
const bootedDevice = await host.boot(selectedDevice);
const session = host.startSession(bootedDevice, {
  onFrame({ width, height, pixels }) { /* upload owned, packed RGBA to native renderer */ },
  onState(state) { /* connecting | streaming | error | closed; detail; inputConnected; screen */ },
});
await session.ready; // Startup finished, not necessarily the first frame. Failures go to onState.
session.sendTouch("begin", 0.5, 0.5); // normalized RAW FRAMEBUFFER coordinates
session.sendTouch("move", 0.6, 0.6);
session.sendTouch("end", 0.6, 0.6);
session.sendText("text");
session.pressButton("home"); // home | back | recents | appSwitcher | power
session.setHingeAngle(90); // only when state.screen.supportsHingeAngle
session.setDisplay("cover"); // inner | cover; only when screen.supportsDisplaySelection and input is ready
session.rotate(); // iOS: toggle portrait / landscape_right; confirmed through screen config
session.setOrientation("portrait"); // iOS: all four DeviceOrientation values
const appearance = await session.getAppearance(); // Android: light | dark | auto readback
await session.setAppearance("dark"); // Android: light | dark; confirmed helper readback
const png = await session.screenshot(); // explicit Save action only; caller chooses destination
session.close(); // REQUIRED on hide, selection change, disposal; stops video, socket and child
host.close(); // also aborts outstanding list/boot requests; permanently closes this host
```

Input methods return whether the command was accepted locally, not a guarantee it was applied remotely. Hinge controls are acknowledged with a five-second timeout and allow one outstanding request. Android text is split at Unicode boundaries into at most 64 packets of 300 UTF-8 bytes; oversized text is rejected before any text is sent. iOS HID cannot represent arbitrary Unicode text and `sendText` explicitly returns false with a state detail. iOS Back and unsupported hinge controls similarly report a reason. Input is gated on socket readiness and, for serve-sim, input admission and screen availability. Avoid calling input methods after the session ends.

## Functional rail controls

The host exports `capabilities(device): DeviceControlCapabilities` and the session publishes the same `{rotate, appearance, screenshot}` flags in `DeviceState.capabilities`. These describe implemented wire transports, not instantaneous readiness or successful remote probing: iOS rotation, Android appearance, and screenshots on both platforms are implemented for booted nonphysical devices. A closed host or off/physical device has all flags false. REST 404/405/501 responses disable the corresponding capability for that host/device without disconnecting video; auth errors, timeouts, and transient operation failures do not claim the protocol is unsupported. Reconnecting with a new host resets this remembered version incompatibility. There are no automatic capability probes, captures, or setting changes on session startup. Parent UI should also gate rotation on `status === "streaming"`, `inputConnected`, and no pending orientation/display/hinge control; await REST promises and disable duplicate actions while pending.

- `session.setOrientation(value: DeviceOrientation): boolean`, where values are `portrait | portrait_upside_down | landscape_left | landscape_right`, sends iOS binary tag `0x07` with `{orientation:value}`. `rotate()` toggles between portrait and landscape_right using authoritative screen orientation. It releases an existing touch before sending, serializes against hinge/display controls, gates input during the request, and publishes `orientationChange: {requested}` separately from `screen.orientation`. There is **no correlated request ID or ack packet** for this tag. Only a subsequent matching screen-config orientation confirms it; unrelated config or `0x90` replies do not. A five-second timeout clears pending state, reports an orientation-lock/readback warning, restores safe raw-frame input, and keeps the stream/socket/decoder alive. Video frames continue during rotation. Closing cancels its timer. Parent should not optimistically rotate screen metadata from the requested value.
- `host.getAppearance(device, signal?): Promise<DeviceAppearance>` and `host.setAppearance(device, "light" | "dark", signal?): Promise<DeviceAppearance>` implement Android GET/POST `/vendor/serve-emu/api/uimode?device=...`. The wire uses `{night:"yes"}` for dark and `{night:"no"}` for light; GET may also report `auto`. `DeviceAppearance` is `light | dark | auto`. Setter readback must match the requested value. Session wrappers `getAppearance()`/`setAppearance()` bind cancellation to session lifetime and publish confirmed values in `DeviceState.appearance`; failed writes do not publish a requested preview.
- `host.screenshot(device, signal?): Promise<Uint8Array>` and `session.screenshot(): Promise<Uint8Array>` use bodyless POST `/vendor/serve-sim/api/screenshot?device=...` or `/vendor/serve-emu/api/screenshot?device=...`. They return owned PNG bytes, not a GPU/window screenshot, renderer readback, or retained decoded frame. A recognized active iOS Duo adds the documented `display=screenId` query. Pending display/orientation switches are rejected; an associated session/metadata change during capture rejects the stale result. Save is an explicit caller action: the adapter writes no local file, opens no save dialog, and retains no image after returning. Upstream helpers may record a screenshot artifact as part of their explicit capture endpoint. PNG signature/IHDR are validated, streaming response storage is bounded to 32 MiB, and oversized/invalid responses are rejected with body cleanup. The session wrapper is preferred in a panel so hiding cancels body download immediately.

REST controls are serialized per device and reject overlapping requests rather than accumulating capture/setting queues. Appearance uses the normal request timeout (15 seconds by default), screenshot uses 20 seconds; `requestTimeoutMs` overrides either. Explicit caller abort, session hide, and host close settle requests even if an injected transport ignores cancellation; late responses cannot publish state. Session REST failures report `detail` and reject the promise without disconnecting a healthy video feed. Cancellation cannot undo a setting already applied remotely, so do not silently retry a cancelled mutation.

### Compatibility evidence and intentionally disabled actions

T3 `useDeviceControls.ts` dispatches typed server host actions; its rail is not evidence that every action has a helper REST endpoint. `DeviceActions.ts` invokes simctl for iOS appearance and ADB/emulator sensor commands for Android rotation. Its Android orientation implementation explicitly notes that `cmd window user-rotation lock` can change app content while leaving the captured display unchanged. The upstream serve-emu `/api/orientation` endpoint in `src/middleware.ts`/`src/server.ts` calls `adb.ts:setUserRotation`, which only sets that user policy and reads it back. It accepts `auto | portrait | landscape`, not four-way physical orientation. This adapter therefore leaves Android **screen rotation** capability false rather than presenting policy changes as a reliable Rotate action. iOS appearance capability is false: no straightforward appearance REST endpoint was found in the inspected serve-sim middleware, and executing arbitrary host commands over a guessed RPC is not implemented.

Confirmed sources: T3 `client-runtime/src/device/stream.ts` uses orientation tag `0x07`; serve-sim `src/device-session.ts:case 0x07` broadcasts screen readback after successful native orientation. serve-sim `src/middleware.ts:/api/screenshot` explicitly supports POST returning PNG and optional numeric display selection. T3 `DeviceHubOperations.ts:screenshot` uses the same vendor-prefixed POST on both platforms. Upstream serve-emu `src/middleware.ts` and `src/server.ts` confirm `/api/uimode` GET/POST and `/api/screenshot`; `uiModeResponse` returns `night: yes | no | auto`. Sources were inspected, not copied. No new ffmpeg or hardware-decode path is needed for explicit screenshots.

Home remains `session.pressButton("home")`. Tools/More menus can call the APIs above; 3D/Flat, view Reset, model keyboard presentation, and Close remain parent UI/view actions, not fabricated remote device commands. Arbitrary iOS text entry is still explicitly unsupported by the existing HID text adapter; these controls do not pretend to implement a keyboard toggle or device reset/reboot.

The native element displays decoded framebuffer pixels with their original orientation, so do not apply an additional orientation transform to input. Use `deviceContentRect(viewRect, frameWidth, frameHeight)` for contain-fit bounds and `pointerToDevice(pointerX, pointerY, contentRect)` to ignore letterbox hits. Pass `true` as its fourth argument only for an already-captured drag to clamp moves/releases outside the content rect. Release pointer capture when hiding/switching devices. Upload synchronously or retain only the latest frame in the UI; asynchronous renderer queues are owned by the caller.

## Duo display state and selection

`DeviceDisplay` is `"inner" | "cover"`; `session.setDisplay(display): boolean` returns whether the request was accepted locally, **not** whether the display has switched. A no-op request for the already elected panel returns true without sending a command, but only when the session is streaming and input-ready. Selection requires iOS serve-sim, admitted/available input, confirmed hinge and physical-orientation capabilities, a recognized elected panel, fresh video, and no outstanding hinge/display control. Hinge and display controls share the request ID sequence and cannot overlap. Physical-pose selection does not silently change the hinge angle to make a rejected pose eligible.

`DeviceScreen` exports these fields through `onState(state.screen)`:

- `width`, `height`, `orientation`: authoritative hub configuration dimensions/orientation, independent of decoded/downscaled pixel sizes.
- `screenId?`: validated nonnegative integer identifying serve-sim's elected screen. For hinge-capable Duo, 1 is cover and 3 is inner. Other IDs are retained but not mapped to invented panels.
- `activeDisplayId?`, `displayId?`: validated numeric metadata retained verbatim if a hub supplies it. The inspected serve-sim backend and T3 stream schema use **screenId**, not these aliases; aliases alone never authorize panel selection or input routing.
- `activeDisplay?`: derived from a recognized `screenId` **and** `supportsHingeAngle`; never inferred from a device name, hinge angle, dimensions, requested panel, or acknowledgement. A non-foldable phone's screen 1 is not labeled cover.
- `supportsDisplaySelection?`: parser always supplies a boolean, true only with hinge capability, `supportsPhysicalOrientation === true`, and a recognized elected panel. This is permission to attempt the supported physical-pose command, not a promise the current hinge pose accepts both displays.
- `supportsHingeAngle`, `supportsPhysicalOrientation?`, `inputUnavailable`: reported capability/readiness flags. Missing hinge/input flags default false; missing physical-orientation capability does not authorize selection.
- `hingeAngle?`, `hingePose?` (`closed | book | open | laptop | tent | null`), `physicalOrientation?` (`portrait | pud | landscape-left | landscape-right | faceup | facedown`), `tableMode?`, `tableModeAvailable?`: validated reported pose state, retained without optimistic command previews.

`DeviceState.displaySwitch?` contains `{ requested: DeviceDisplay, acknowledged: boolean }`. It is pending/requested state, deliberately separate from `screen.activeDisplay`. On acceptance the adapter ends its existing touch on the old display, disables all input, and stops presenting frames until the matching acknowledgement and target election are both observed. Target config and acknowledgement may arrive in either order. Any elected-display change (including an external fold) invalidates the decoder generation, aborts/cancels the old AVCC request, reopens the active feed with a fresh decoder, and gates input until fresh video. Only a new-generation frame after acknowledgement/election clears `displaySwitch` and restores readiness. Old-generation frames/errors cannot escape into the new panel. UI must render `screen.activeDisplay`, not the requested value, and release pointer capture while input is gated; stale move/end events cannot resume an old gesture without a new begin.

A negative acknowledgement or a five-second timeout closes the uncertain session and reports an error; reconnect is required before further input. A successful command acknowledgement alone never optimistically elects a display. Closing also cancels the handoff timer and clears pending state.

### Exact protocol evidence and limits

T3 reference `apps/web/src/components/device/DeviceDuoViewport.tsx:71–75` maps panel 1 to `{control:"physical", value:"facedown"}` and panel 3 to `faceup`. `packages/client-runtime/src/device/stream.ts:450–469` requires input admission, hinge capability, and physical-orientation capability before sending tagged JSON `0x10` with `{requestId,command}`. Its screen schema uses `screenId`; its `0x90` handler forwards `{requestId,ok,error?}`. The active-feed reopen on elected-screen change follows the same reference's `stream.ts:1138–1147`; fixed-panel feed selection is not a native display-election command.

The upstream backend independently confirms this: https://github.com/expo/expo-device-hub/blob/main/packages/serve-sim/packages/serve-sim/src/device-session.ts (`case 0x10`, `queueHingeControl`, `screenConfig`, `readScreenFromNative`) validates physical commands, returns a correlated `0x90` acknowledgement, publishes `screenId`/`supportsPhysicalOrientation` under config `0x82`, and routes HID to the captured elected screen. `hinge-control.ts` allows `physical: faceup | facedown`. The inspected backend can reject facedown unless the observed hinge angle is strictly between 0 and 180. No `setDisplay`/`selectDisplay` wire command, `activeDisplayId`/`displayId` alias semantics, or unconditional forced panel-election endpoint was found. This adapter therefore sends only the documented physical control and waits for native election; it does not fabricate commands or claim both panels are selectable in every pose. Source was inspected, not copied.

## Protocol and supported transports

Implemented independently using wire observations in the T3 reference (`packages/client-runtime/src/device/stream.ts`, server `DeviceHubOperations.ts`) and expo-device-hub npm metadata (0.19.1, repository https://github.com/expo/expo-device-hub). No upstream source is incorporated.

- `GET /api/devices` returns `simulators`, `emulators`, optional `errors`; Android discovery includes only what the hub reports (no local SDK probing).
- Explicit boot: `POST /api/devices/boot` with `{platform,id,name}`; returned serial/ID is preserved for the next connection.
- iOS: attach an already-booted simulator through `POST /vendor/serve-sim/grid/api/start` with `{udid}`. Probe `/vendor/serve-sim/api?device=...`, then stream `/vendor/serve-sim/helper/{encoded-id}/stream.avcc`: big-endian 32-bit record length including a one-byte tag, tag 1 avcC configuration, 2 keyframe, 3 delta, 4 JPEG seed (ignored). Convert configuration and length-prefixed access units to Annex B for ffmpeg. Input uses `/vendor/serve-sim/helper/ws?device=...`, binary tagged JSON: touch 3, button 4, hinge request 0x10, screen config 0x82, input admission 0x83, hinge reply 0x90. Older helpers require one bounded MJPEG request to prime capture/HID; one fragment is discarded and the request is cancelled. It is never presented, repeated, or used as a video source.
- Android: probe `/vendor/serve-emu/api?device=...`, connect `/vendor/serve-emu/ws?device=...&frame-meta=1`. Strip optional 16-byte SEMU v1 metadata; feed Annex B to ffmpeg. JSON touch/text/hardware input shares the socket; `reset-video` requests a fresh encoder keyframe.
- Explicit WebRTC-only settings or an AVCC transport lock produce an error. No browser/WebRTC implementation, MJPEG video fallback, screenshot loop, physical-device stream, automatic retry, or Android serve-sim/Simlock autodetection is provided. Reconnect by creating a fresh session. ffmpeg must be installed/configured separately; no shell is used and the executable path is one literal argument.

## Resource bounds and verification

ffmpeg applies a fixed contain-scale limit of 1280 pixels on the longest output edge, preserving aspect ratio to integer-pixel rounding and never upscaling smaller inputs. Scaling happens before packed RGBA crosses the CPU pipe or reaches the renderer, reducing copy/upload traffic from high-resolution simulators. Both H.264 decoder threads and filter threads are limited to one; no hardware decoding is selected. `DeviceFrame.width`/`height` describe these scaled pixels, while `DeviceState.screen` retains the native screen metadata reported by the hub. Normalized touch coordinates remain valid regardless of this downscale. There is no additional scale configuration in this first pass.

Wire packets and decoder input are limited to 8 MiB, Android pending input to 64 video packets, decoded frames to 64 MiB, PAM headers to 1 KiB, and diagnostic stderr to 4 KiB. Decoded delivery coalesces to one latest pending frame plus a frame under assembly. HTTP video is consumed with decoder backpressure; WebSocket backlog overflow stops the stream rather than dropping dependent H.264 data. Decode inactivity times out after 15 seconds. `close()` aborts session fetches and closes the WebSocket/pipes, sends SIGTERM to ffmpeg, then SIGKILL if needed after 500 ms. Superseded listings and sessions cannot publish stale results.

A changed H.264 SPS restarts the ffmpeg child, because PAM encoders can retain their initial dimensions even after an input resolution change. Pending frames from the previous configuration are invalidated before restarting. SPS input is bounded to 64 KiB; decoder writes must contain complete hub access units or configuration records, not arbitrary network fragments (the host performs that framing).

Tests include injected HTTP/socket/decoder transports, fragmented and corrupt wire records, admission and capability gating, hide/stale-request cleanup, pointer mapping, bounded frame coalescing, and real ffmpeg H.264-to-RGBA decoding through an actual local HTTP/WebSocket fake hub. The real-codec tests require ffmpeg with libx264 and lavfi. Live simulator/emulator validation still requires a user-supplied hub and booted device.
