neoism-agent edit/write/apply_patch tools attach LSP diagnostics post-mutation (opencode parity). `crate::lsp::diagnostics`/`touch_document` are **synchronous blocking** (each does `wait_for_notification` up to `DIAGNOSTIC_TIMEOUT` = 2s). Running them directly in the async tool fn blocks the tokio worker and **freezes the model/agent response after an edit**.

A prior model "fixed" the freeze by stubbing `tool_support/diagnostics.rs` to emit `{diagnosticsSkipped:true}` placeholders — a regression that also left 2 aspirational tests red.

**Correct (golden) fix:** real diagnostics, but the metadata builders (`write_tool_metadata`, `edit_tool_metadata`, `apply_v4a_patch_metadata`, and the unified-diff block in `apply_patch_tool`) must run inside `tokio::task::spawn_blocking` — never on the async executor.

`diagnostics.rs` now mirrors opencode `LSP.Diagnostic.report/pretty`: `attach_lsp_diagnostics` returns `Option<String>` "LSP errors detected in this file, please fix:\n<diagnostics file=...>\nERROR [l:c] msg\n</diagnostics>" appended to tool output (errors only, cap 20/file). Metadata: `diagnostics` array (touched files first w/ `source:"touched"`, then bounded `source:"project"` from `lsp::cached_project_diagnostics`), `diagnosticsCount`, `diagnosticsProjectFileLimit`=8, `diagnosticsProjectScanLimit`=200.

**Single-wait (latency) rule — opencode-faithful:** `touch_paths` (→`lsp::touch_document`→`lsp_service::touch`) is the ONE blocking diagnostics step and it caches into the service `diagnostics` map = opencode `touchFile(_,"document")`. `attach_lsp_diagnostics` then does a pure cache read via `lsp::cached_diagnostics` (NOT `lsp::diagnostics`, which would do a 2nd fresh wait) = opencode `diagnostics()` reading `client.diagnostics`. So every mutation path MUST call `touch_paths` before `attach_lsp_diagnostics`; all four (write/edit/v4a/unified-diff) do. Earlier bug: calling both `lsp::touch_document` and `lsp::diagnostics` doubled the per-file wait (~4s). No-LSP-binary path stays instant (`file_query_specs` filters by `command_available`). Cold start: first edit per language spawns+initializes the server inside `with_client`.

**Per-edit latency fix (2026-06-24) — pull diagnostics + short ceiling.** The blocking `wait_for_notification("publishDiagnostics", DIAGNOSTIC_TIMEOUT=2s)` in `lsp_service::touch` hit the FULL 2s on EVERY Rust edit because rust-analyzer only pushes diagnostics after `cargo check`/flycheck (seconds later), not on didChange/didSave — so every edit/write/patch stalled ~2s (felt as "agent much slower at edits/reading/talking"). opencode stays fast by PULLING (`textDocument/diagnostic`, LSP 3.17) instead of waiting for the push. Fix mirrors that: declare `textDocument.diagnostic` client capability (`lsp_client.rs`), parse `diagnosticProvider` into `InitializeResult.diagnostic_provider`, add `StdioLspClient::pull_diagnostics(file,timeout)` (returns the report's `items` reshaped as `{uri,diagnostics}` for `parse_diagnostics`). `touch` now: ensure_open+save → if `diagnostic_provider` pull (fast, returns whatever's ready) → else short `publishDiagnostics` wait bounded by new `TOUCH_DIAGNOSTIC_TIMEOUT=600ms` (NOT the 2s `DIAGNOSTIC_TIMEOUT`, which the explicit `diagnostics` tool still uses). Slow flycheck errors land in the cache and surface on the NEXT tool call = opencode's eventually-consistent model. Still inside spawn_blocking. VERIFIED: the rust-analyzer on this machine (2026-04-27, the 50MB `…rust-analyzer-unwrapped…/bin/rust-analyzer` in the nix store) DOES advertise `diagnosticProvider` (`interFileDependencies:true, workspaceDiagnostics:false`) → Rust uses the fast pull path, the 600ms wait branch is never hit for Rust here. Per-file pull only (workspaceDiagnostics false) — matches our single-file `textDocument/diagnostic`. Aside: the bare `rust-analyzer` on PATH in an interactive shell resolves to a broken rustup shim that errors; neoism spawns the working nix binary, so this only matters if Rust LSP ever silently no-ops.

**GUI diagnostics footer (desktop diff card).** opencode TUI shows diff THEN diagnostics; neoism's desktop diff card (`neoism-ui` `panels/agent_pane/view/tool_message.rs` `render_tool_diff_cards`) previously rendered only the green/red rows even though the data was in `metadata.diagnostics`. Added: `ToolDiffSection.diagnostics: Vec<DiagLine>` populated by `attach_section_diagnostics` (matches metadata entry `path` to section `link_target`; "project" entries for other files drop out), measured via `diag_footer_height`, painted by `render_diff_card_diagnostics` (errors red / warnings yellow, cap `MAX_DIAG_LINES_PER_CARD=6` + "+N more"). The diff-section cache key hashes `detail`, so it invalidates when diagnostics update.

**Why:** blocking I/O on the tokio executor stalls everything sharing that worker.
**How to apply:** any new neoism-agent tool that calls blocking LSP/format/git helpers must wrap them in spawn_blocking. Severity strings are lowercase `error/warning/information/hint`; positions are 0-based. See [[no-reentrant-mutex]], [[live-edit-model]].
