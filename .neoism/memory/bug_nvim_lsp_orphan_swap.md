Symptom: cold launch fast; after ANY nvim editor is opened, new-window AND Cmd+W (and even unrelated apps like the file manager) get slow. 100s of agents missed it because they profiled the launch code path — the cause is environmental, not in the launch code.

Root cause (proven 2026-06-25): embedded `nvim --embed` spawns LSP servers (rust-analyzer, tsserver, json). nvim was NOT a process-group leader and shutdown used `start_kill()` / `kill_on_drop` which SIGKILL only nvim — orphaning the language servers to init. Idle rust-analyzers (multiple GB each; observed two holding ~7.5 GB) accumulate and push the machine into swap. CPU is fine (load ~2 / 24 cores); MEMORY/SWAP is the bottleneck. Every subsequent process launch (neoism windows + external apps) then stalls on swap-in. "Only after nvim opened" = before that there is no rust-analyzer and no swap.

Fix landed: spawn nvim with `process_group(0)` (pgid == nvim pid), publish the pid, and on Drop `kill(-pgid, SIGKILL)` to reap the WHOLE subtree at once. `kill()` only delivers the signal (returns immediately) so it stays off the Cmd+W critical path. Each nvim gets its own group, so reaping one editor never touches another open workspace. Done in BOTH paths: desktop local `neoism-backend/src/performer/nvim.rs` (NvimEmbedMachine, build_nvim_command, run_nvim_runtime, Drop) and daemon `neoism-workspace-daemon/src/nvim.rs` (NvimSession).

Note: lua `rio/lsp.lua` already dedups LSP clients by name+root_dir, so multiple rust-analyzers/tsservers in one nvim are one-per-project-root (expected), not a dedup bug.

SECOND root cause — slow Cmd+W QUIT (confirmed 2026-06-25 by `[close-timing]` eprintln instrumentation): the neoism close handler itself is instant (~49µs). The stall was `EmbeddedDaemonHandle::drop` in `neoism-frontend/desktop/src/embedded_daemon.rs` doing a plain unbounded `handle.join()` on the embedded daemon's tokio runtime thread (the old comment claimed it didn't block indefinitely — it did). On last-window quit the process blocked until the daemon drained; after an editor/LSP/index session there's more to drain → "slow only after nvim opened" quit. Fix: detach the join onto a helper thread + `recv_timeout(150ms)` bound, then let the OS reap at exit. Durability-safe (daemon persists per-delta on each edit, not at shutdown). User confirmed quit now instant. Method that worked: add `[close-timing]` Instant eprintlns to the close path (handle_close_requested, close_tab, the Drop), rebuild, read the breakdown — beats guessing.

THIRD root cause — slow COLD START (fixed 2026-06-25): `main()` calls `resolve_daemon()` (main.rs:1161) BEFORE creating the event loop/window (1171-1188), and it blocked on `EmbeddedDaemonHandle::spawn()`'s `ready_rx.recv()`. The daemon only signalled ready AFTER its full bootstrap: unix bind + auth bootstrap + workspace bootstrap + paired-hosts load + axum router build + a synchronous `tailscale ip -4` SUBPROCESS (`embedded_tcp_bind_addrs`/`tailscale_ipv4`) + TCP 7878 binds. So every launch waited for all of that before the window could paint — a cost bare terminals (ghostty/alacritty) don't pay. `tailscale ip -4` measured 8-34ms when tailscaled is healthy but can hang for seconds when it's restarting/offline. Fix (`neoism-frontend/desktop/src/embedded_daemon.rs`): move `ready_tx.send(Ok(()))` to immediately after `UnixListener::bind` succeeds; all bootstrap (auth/workspace/router/tailscale/TCP) now runs concurrently on the daemon thread while the desktop proceeds to paint. Bound socket is all the caller needs to avoid racing a second daemon; early connections queue in the listener backlog. Auth-bootstrap failure now logs + exits the thread (can't report via ready anymore) and the desktop degrades to daemon-less, same as a spawn failure. NOTE: wgpu device init + shader compile + font/fontconfig load (inside application.run()) is the OTHER cold cost — shared with ghostty, not yet profiled.

FOURTH root cause — slow COLD WINDOW LAUNCH (fixed 2026-06-26, the big one): on Parker's hybrid laptop (NVIDIA RTX 5070 dGPU + AMD 890M iGPU, Hyprland/Wayland), cold launch took ~2.5-2.7s. Localized via `[launch-timing]`/`[gpu-select]` eprintlns down to ONE call: `vkCreateInstance` = 2.72s. Cause: the Vulkan loader dlopens EVERY installed ICD to enumerate adapters, including the NVIDIA driver, whose init RESUMES the runtime-suspended dGPU from D3cold (~2s). neoism renders only on the iGPU (sugarloaf's Wayland scoring already prefers integrated 2000 > discrete 1500), so loading NVIDIA was pure tax. Signature: cold/after-idle = slow (dGPU asleep, gets woken), open-another-right-after = fast (dGPU still awake from autosuspend delay). NOT power-mgmt of the iGPU (it's always on), NOT LLVM (libLLVM-22.so is 171MB but create_device was 2.5ms), NOT pipeline cache (22KB loads fine), NOT the daemon (847µs). Proven: `VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/radeon_icd.json ./neoism` → create_instance 2.72s→36ms, total Screen::new 2.75s→81ms.

Fix (`sugarloaf/src/context/vulkan.rs`): `restrict_icds_avoiding_dgpu()` + `IcdEnvGuard` — before `create_instance`, when preference is Integrated or Auto-on-Wayland and an NVIDIA ICD exists alongside ≥1 non-NVIDIA ICD, set `VK_ICD_FILENAMES` to just the non-NVIDIA manifests, then RESTORE via RAII guard right after instance creation (so child PTYs/GPU apps keep full driver access — don't set it process-wide, it'd lock terminal children to the iGPU and break `__NV_PRIME_RENDER_OFFLOAD`). Respects user-set VK_ICD_FILENAMES/VK_DRIVER_FILES/VK_LOADER_DRIVERS_DISABLE and NEOISM_VULKAN_DEVICE=discrete. Method that cracked it: nested `[launch-timing]` eprintlns from main()→from_target→Sugarloaf::new→VulkanContext::new phases; the warm/cold inconsistency = whether the dGPU happened to be asleep.
